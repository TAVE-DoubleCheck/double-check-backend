# 하루 업무 처리 뼈대

## 범위

`DailyWorkService.advanceTo(targetDate)`는 업무 날짜를 목표 날짜까지 하루씩 이동한다.
각 날짜에 청구서 발행 → 자동이체 → 미납·실효 → 만기 → 장부 대사를 실행한다.
서버의 실제 날짜를 기준으로 실행하는 스케줄러가 아닌, 가상 업무 날짜를 이동하는 내부 서비스이다.

이번 구현은 연결 구조이다. 실제 업무 로직, LedgerService, 외부 날짜 변경 API,
관리자 인증 및 실행 이력 테이블은 포함하지 않는다. 새 Flyway 파일도 필요하지 않다.

## 담당 기능 연결

`DailyWorkStep`을 구현한 Spring 빈을 각 단계에 하나씩 등록한다.

| stage | 담당 업무 |
|---|---|
| BILLING | 청구서 발행 |
| AUTO_DEBIT | 자동이체 및 LedgerService를 통한 입금 기록 |
| LAPSE | 미납·실효 처리 |
| MATURITY | 만기 처리 |
| RECONCILIATION | 장부 대사 |

BILLING·AUTO_DEBIT·LAPSE·MATURITY는 BE B가 구현했다 (`kr.tave.minicore.contract.batch`, `docs/contract-payment.md`).
RECONCILIATION이 등록되면 날짜 이동을 실행할 수 있다.

빈 등록 순서와 관계없이 위 순서로 실행한다. 한 단계에 두 빈을 등록하면 기동에 실패한다.
한 단계라도 구현이 없으면 날짜 이동 전에 실행을 거부한다. 로그만 남기고 성공하는 임시 빈은 두지 않는다.
현재 실제 단계 구현이 없으므로 애플리케이션은 정상 기동하지만 날짜 이동은 실행할 수 없다.
테스트에서만 다섯 단계를 대신하는 테스트 빈을 등록한다. 이때 실제 계약 단계 빈과 겹치지 않도록
`daily.contract-steps.enabled=false`로 계약 단계 빈을 끈다.

각 단계는 전달받은 날짜를 사용한다. 같은 트랜잭션에서 `ClockService.today()`로 읽는 날짜도 같다.
기존 서비스에 연결할 때는 기본 REQUIRED 또는 MANDATORY로 호출자의 트랜잭션에 참여한다.
REQUIRES_NEW, 비동기 실행, 예외 무시, 외부 API를 통한 실제 출금 등은 이 롤백 보장의 대상이 될 수 없다.
업무 실패는 RuntimeException으로 전파해야 하며, 검사 예외는 RuntimeException으로 변환한다.
입출금 기록은 납부·지급 완료 변경 후 LedgerService를 호출하여 같은 트랜잭션에서 처리한다.

## 날짜와 트랜잭션

1. 하루마다 새 트랜잭션을 시작한다.
2. `system_clock`의 id=1 행을 SELECT FOR UPDATE로 잠근 뒤 현재 날짜를 읽는다.
3. 다음 날로 날짜를 변경한다. 아직 다른 트랜잭션에 확정되지 않은 상태이다.
4. 다섯 단계를 순서대로 실행한다.
5. 모두 성공하면 날짜와 업무 데이터를 함께 커밋한다.

실패하면 그날의 날짜 변경과 업무 데이터를 함께 롤백한다. 이전에 완료한 날은 유지한다.
예를 들어 1일에서 4일로 이동하다 3일에 실패하면 DB 날짜는 2일이고, 재시도는 3일부터 진행한다.
단계 실행 중 발생한 RuntimeException은 `DailyWorkException`으로 전달하며 failedDate에서 실패한 날짜를 확인한다.
트랜잭션 시작·커밋 오류는 Spring의 원래 예외로 전달될 수 있다.
응답 유실 후 같은 목표 날짜를 다시 요청해도 이미 완료한 날은 다시 실행하지 않는다.

동일 날짜 요청은 아무 작업도 하지 않는다. 첫 잠금 시점에 과거인 목표 날짜는 거부한다.
동시 요청 사이에 다른 요청이 목표 이상으로 이동했으면 진행 중인 요청은 추가 처리 없이 종료한다.
반환값은 해당 요청이 도달한 목표 날짜이며, 다른 요청에 의해 DB 날짜가 더 앞으로 갈 수 있다.
전체 기간을 묶는 외부 트랜잭션은 허용하지 않는다(`Propagation.NEVER`). Spring 빈을 통해 호출한다.

## 동시 처리 범위

DB 행 잠금은 같은 DB를 사용하는 여러 서버의 날짜 이동 요청도 직렬화한다.
청구서·ledger 등의 업무상 중복 방지는 각 담당 기능의 UNIQUE 등으로 별도 보장해야 한다.
일반 계약·수동 납부·지급 API까지 이 잠금에 자동으로 참여하는 것은 아니다.
해당 API와 날짜 이동을 동시에 허용할지는 팀이 별도로 정해야 한다.
날짜를 직접 UPDATE하는 호출은 이 서비스를 우회하므로 운영에서 사용하지 않는다.

## 테스트

```bash
./gradlew test --tests 'kr.tave.minicore.daily.DailyWorkIntegrationTest'
```

독립적인 Testcontainers PostgreSQL에서 실행 순서, 하루씩 이동, 실패 날짜의 롤백,
재시도, 동일·과거 날짜, 미구현·중복 단계, 외부 트랜잭션 거부와 동시 실행을 확인한다.
동시 실행 테스트는 두 번째 요청이 실제 DB 잠금을 기다리는지 확인한다.
